# トークン見積もり:最終テスト(リリース直前・2026-11-25)

Geminiを `gemini-3.5-flash-lite` に固定し、従量課金に切り替えたあと(versionCode 192〜)の、最終のテストです。
**見積もりが、実際の消費トークンより少なく、かつ、離れすぎていないか**を確かめます。
過去の測定は `docs/token_estimation_test_cases.md`(2026-10〜11)。プロンプトとモデルが変わったので、この表で測り直します。

## 合格の基準

- **目安 ÷ 合計(実測)** が **50%〜100%**(2026-11-25に、ユーザーが決定)。100%を超えたら、目安が多すぎるので、係数を下げる。50%より低ければ、少なすぎるので、係数を上げる。
- 思考(考える分のトークン)は、毎回0〜500でばらつくので、**見積もりに含めない**。そのため、思考が多い回は、50%近くまで下がることを許容する。
- 係数は、「思考を除いた実測(入力+出力)」の約80%にそろえてある。思考が0の回は約70〜80%、思考が約500の回は約50%になる。
- 失敗したときは、文言(エラーの案内)と、AppLogの行を控える。トークンが減っていないことも確認する。

## 準備

1. **Lambda(ai-chat)の `MONTHLY_LIMIT_TOKENS` の `FREE` を、一時的に大きくする**(例: `2_000_000`)。Deployする。
   - 本番は `10_000`。**テストが終わったら、必ず `10_000` に戻して、Deployする**(戻し忘れると、全員の無料枠が大きくなる)。
   - E区分(枠の不足)のテストの前に、`10_000` に戻して、アプリを入れ直す(使用量は、端末ごとに数えられるため)。
2. GPTのテスト(D区分)をするときは、Lambdaの環境変数 `GPT_ENABLED` が `true` であること。
3. アプリは versionCode 192以降。AIは、設定の「使うAI」で、Gemini / GPT を切り替える。
4. **同じ日・同じ写真・同じ投稿・同じ履歴・同じメモ**を使い、変えるのは、ケースで決めた部分だけにする。
5. 材料: 1月の日記31件(テスト用)、写真(標準サイズ。D1の3枚と同じ)、行動履歴が多い日、Xの投稿。

## 記録のしかた

1. 作成画面の「消費トークンの目安」を控える(「目安」の列)。
2. 生成したら、CloudWatch Logs(ai-chatのLambda)で、時刻が合う行を探す。
   - Gemini: `{"provider": "Gemini", "model": "gemini-3.5-flash-lite", "prompt": …, "output": …, "thoughts": …, "total": …, "seconds": …}`
   - GPT: `{"provider": "OpenAI", "model": "gpt-5-mini", "input": …, "output": …, "reasoning": …, "total": …}`
   - モデル名が `gemini-3.5-flash-lite` になっていること(固定したため)も確認する。
3. 「入力・出力・思考・合計・秒」を、チャットに貼る。**目安÷合計は、私が計算して、表に記入する**。
4. 数ケースずつ、まとめて貼ってよい。

## 写真の撮影日時を送るようにした(2026-11-25)

複数日の日記で、AIが、どの日の写真か分からないため、写真ごとに、撮影日時の行(「1枚目: 2026年1月1日 09:30」)を、プロンプトに足した(撮影した場所は、送らない)。

## 係数の修正(2026-11-25、A1〜A6のあと)

A2が不合格(50%)で、さらに、量が増えるほど見積もり÷実測が高くなる(A1 64%→A4 87%→A6 90%)ことが分かった。
固定の分(指示文・出力)と、1つあたりの分(メモ・写真)で、実測に対する割合が違うためだった。
そこで、Geminiの、ふつうのAI日記の係数を、**すべて、実測の約80%にそろえた**(`token_estimator.dart`)。
A7〜A10は、修正後のビルド(versionCode 193〜)で測る。

A5・A6が低いのは、思考(235・544)が、見積もりに含まれないため。思考は、ばらつくので、含めない。

日記を1つにする(まとめ)の係数は、日記1文字あたりを0.5のまま変えていない(指示文の+70だけ増える)。Cで測り直す。

## 行動履歴の式(2026-11-25、10件・100件・500件の実測で確定)

履歴の入力トークン(実測)は、10件(約270文字)で540、100件(約3,043文字)で2,829、500件(約15,100文字)で12,804。
この3点は、**「約317 + 0.825 × 文字数」の直線**に、誤差30以内で乗った(500件は、直線を決めたときに使っていない点)。
そこで、その約80%の、**250 + 0.66 × 文字数**にした。文字数が約266文字未満のときは、1文字あたり1.6を上限にする(1件のような小さいサイズで、多くなりすぎないように)。

経緯: 最初は「文字数 × 1.6」(10件で決めた)→ 100件で152%(不合格)→ 段階の式 → 割合の式(9.4 × 文字数^0.68)→ 500件で51%(下がりすぎ)→ 直線の式。

| ケース | 文字数 | 履歴の見積もり | 履歴の入力(実測) | 比 |
|---|---|---|---|---|
| 10件 | 270 | 428 | 540 | 79% |
| 10件・6日分 | 314 | 457 | 585 | 78% |
| 10件・住所つき | 348 | 480 | 614 | 78% |
| 100件 | 3,043 | 2,258 | 2,829 | 80% |
| **500件** | 15,100 | **10,216** | 12,804 | **80%** |

一定の分(約317)が、何のトークンなのかは、分かっていない。1件・3件・30件の測定で、少ない側が合うか確かめる。

## 既知の懸念(2026-11-25、ユーザーが了承)

行動履歴を選ぶと、思考(約300〜500トークン)が出ることが多く、そのとき、見積もり÷実測は、**50〜58%**まで下がる(思考を除くと約73%)。
思考は、毎回0〜500でばらつくので、見積もりに含めない方針。見積もりが少なすぎる側(足りないのに、足りると出る側)で、許容する。公開後に、実際の利用で、ずれが大きいときは、思考の分を、見積もりに足すことを検討する。

## E. 見積もりのダイアログと、使用量の整合

**準備**: LambdaのFREEを `10_000` に戻してDeployし、アプリを入れ直す(新しい端末として、使用量を0にする)。

| ID | 条件 | 手順・ねらい | 結果 |
|---|---|---|---|
| E1 | 残りが目安より少し下 →「やめる」 | 「トークンが足りません」のダイアログが出る。「やめる」で、生成されず、使用量が増えない。「それでも送る」は、なくなった(足りない見込みのときは、AIに送れない)。文末に「来月の1日に戻ります。それまで待つか、ゲームでポイントを貯めて、トークンに交換してください」と出る | |
| E2 | 目安が残り以下で、実際の消費が残りを超える | 見積もりは約80%なので、実際は超えることがある。広告のあと、生成される。使用量の増え方が、CloudWatchの「合計」と同じか。枠を超えたときの表示(例: 10,200 / 10,000) | |
| E2-2 | 目安が残りを超える →「ポイント・トークンを見る」 | ポイントのページへ進む。AIには送られず、使用量が増えない | |
| E3 | アカウント紐づけあり: 枠 → 残高の順 | 枠の残りが少ない状態で生成。枠が先に0になってから、残高が引かれる | |
| E4 | 設定の「使用量」の表示 | 無料枠(毎月10,000)と、交換したトークンの表示。「無料枠がなくなってから」の表記 | |
| E5 | 使い切ったあとの生成 | 「今月の使用量の上限」の案内と、トークン交換への案内が出る。AIは呼ばれない | |
