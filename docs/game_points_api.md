# ゲームアプリから、ポイントを貯めるAPI

4つのゲームアプリ(KamoooneShot・脱出ゲーム２・3・4)が使うAPI。
ポイントの獲得と交換は、すべてサーバーとWebで行う。ゲームは、「紐づけ」と「成果の通知」だけを行う。

- ベースURL: ポイントのAPI(`server/points_web/config.js` の `apiBase` と同じ)
- アカウントがなくても、ゲームは普通に遊べる。紐づけは、ポイントを貯めたい人だけが行う(任意)。

## アプリID

| アプリID | 表示名 |
|---|---|
| `kamoooneshot` | KamoooneShot |
| `escape_2` | 脱出ゲーム２ |
| `escape_3` | 脱出ゲーム3 |
| `escape_4` | 脱出ゲーム4 |

アプリIDと表示名は、`server/points_api/lambda_function.py` の `APPS` で変えられる。

## アプリのキー

- ゲームごとに、秘密のキーを1つ持つ。`python3 tools/make_app_key.py <アプリID>` で作る。
- キーは、ゲームに入れる。サーバーには、キーの **ハッシュだけ** を、環境変数 `APP_KEY_HASHES` で渡す。
- すべてのリクエストに、ヘッダー `X-App-Key: <キー>` を付ける。
- 注意: アプリに入れたキーは、解析すれば取り出せる。キーは「通りがかりの悪用を防ぐ最初の守り」で、
  不正の被害を止めるのは、サーバー側の上限(下の「ルールと上限」)。
- キーは、リポジトリにコミットしない(`.env` などに入れ、`.gitignore` に入れる)。

## 1. 紐づけ(アカウントとつなぐ)

auto_diary の「ポイント・トークン」と同じ流れ。ゲームの画面に「ポイントを貯める」ボタンを置く。

1. `POST /pairing/start`
   - ヘッダー: `X-App-Key`
   - 本文: `{"appId": "kamoooneshot", "label": "iPad"}`(`label` は端末の名前。Webの確認画面に出る)
   - 応答: `{"code": "123456", "claimSecret": "...", "expiresAt": 1792422783}`
   - `code` を画面に表示する。`claimSecret` は画面に出さず、アプリの中だけに持つ。コードは10分で失効。
2. ユーザーが、Webにログインして、コードを入力する(確認画面に、ゲーム名と端末名が出る)。
   - 同じ端末なら、「Webを開く」で `…/index.html?pair=123456` を開くと、入力欄にコードが入る。
3. `POST /pairing/claim`(数秒おきに呼ぶ)
   - 本文: `{"code": "123456", "claimSecret": "..."}`
   - 202 `{"status": "pending"}`: まだ。待つ。
   - 404 `{"status": "expired"}`: 期限切れ。やり直す。
   - 200 `{"status": "linked", "deviceToken": "..."}`: 完了。**トークンは1回だけ**返る。
4. `deviceToken` を、端末の安全な保存領域(Keystore・Keychain)に保存する。

ユーザーが端末で解除したときは、`POST /device/unlink`(ヘッダー `X-Device-Token`)を呼ぶ。Webの端末一覧からも消える。通信できなくても、端末のトークンは捨てる。

紐づけられる端末は、同じアプリにつき、アカウントごとに3台まで(超えると、Webで確定するときにエラー)。

## 2. 成果を知らせる

`POST /events`

- ヘッダー: `X-App-Key: <キー>`、`X-Device-Token: <deviceToken>`
- 本文: `{"eventId": "<一意のID>", "type": "stage_clear"}`
  - `eventId`: 成果ごとに作る一意のID(8〜64文字の英数字と `-` `_`。UUIDでよい)。
    **通信に失敗したときは、同じ `eventId` で送り直す**(二重に付かない)。
  - `type`: 成果の種類。ポイントの量は送らない(サーバーが決める。送っても無視される)。
- 応答(200):
  - 付いたとき: `{"granted": 50, "points": 1250}`(`points` は、付いたあとのポイント)
  - 付かなかったとき: `{"granted": 0, "reason": "..."}`
    - `duplicate`: 同じ `eventId` で、すでに付いている(送り直しなので、問題ない)
    - `event_limit`: その成果の回数の上限(1日1回など)に達している
    - `daily_ceiling`: 1日に貯められるポイントの上限に達している
- エラー:
  - 401 `invalid_app`: キーが違う
  - 401 `invalid_device_token`: 紐づけが解除された。保存したトークンを捨てて、未紐づけに戻す
  - 403 `app_mismatch`: 別のアプリのトークン
  - 400 `unknown_event` / `invalid_event_id`: 成果の種類や ID が正しくない

ゲームは、紐づけ済みのときだけ送ればよい。未紐づけなら、何も送らない。
成果の通知に失敗しても、ゲームの進行は止めない(あとで送り直すか、あきらめる)。

## ルールと上限(サーバー側。仮の値)

`server/points_api/lambda_function.py` の `EVENT_RULES` で決める。変えるときも、ゲームの更新は要らない。

| 成果の種類 | ポイント | 回数の上限 |
|---|---|---|
| `daily_first_play` | 100 | 1日1回(日本時間) |
| `stage_clear` | 50 | なし(1日の合計の上限まで) |

- 1アカウントが1日(全アプリ合計)に貯められるポイント: `DAILY_POINTS_CEILING`(仮に5,000)。
  普通に遊んでは届かない値にする。キーが盗まれたときの被害を止める安全装置。
- アプリごとに違うルールにするときは、`APP_EVENT_RULES` に書く。
- 新しい成果の種類を足すときは、`EVENT_RULES` に1行足す。この表も直す(直し忘れると、サーバーのテストが失敗する)。

### 成果の名前を足す・変えるときの決まり

成果の名前は、サーバーと各ゲームの両方に書かれている。食い違うと、ポイントが付かなくなる(`unknown_event`)。

1. **足すときは、サーバーが先。** `EVENT_RULES` に足して Lambda を Deploy してから、ゲームを更新する。
2. **名前は変えない。** 変えたいときは、新しい名前を足す。古い名前は、古いゲームのために、サーバーに残す。

## 履歴

付いたポイントは、履歴のテーブル(ledger)に `game_grant` として残る(アプリID・成果の種類つき)。
